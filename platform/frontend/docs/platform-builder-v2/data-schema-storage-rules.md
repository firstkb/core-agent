# Data Schema And Storage Rules

## Purpose

This document captures early rules for how Platform Builder V2 should think about:

- data schema naming
- physical storage naming
- generated system fields
- indexes and relationships
- external locked tables

These rules belong primarily to the data-schema and backend boundary, not to the visible Form Builder UI.

The Form Builder should expose the right concepts, but physical storage policy should remain an explicit backend-aware layer.

## Boundary: Logical Model vs Physical Storage

Platform Builder V2 should distinguish between:

- the visible business name
- the internal model key
- the physical table name

Example:

- visible name: `Customer Profile`
- internal model key: `customer_profile`
- physical table name: `pb_customer_profile`

This separation is important because a good builder UI should use human-readable names, while the backend should use stable storage-safe identifiers.

## Table Naming Rule

The physical table name should use:

- one stable platform prefix
- one short readable storage key derived from the model name

Recommended prefix:

- `pb_`

Recommended table-name pattern:

- `pb_<model_storage_key>`

Examples:

- `pb_customer_profile`
- `pb_site_audit`
- `pb_incident`

## Why Not Use The Legacy `ExtDB1{id}` Pattern

The old `ExtDB1{id}` style proved that a prefix plus table identity can work, but it is not ideal for V2.

Reasons:

- it is less readable
- it hides the meaning of the table
- it ties the physical name too closely to an internal identifier
- it is harder to inspect manually in PostgreSQL

Recommended V2 rule:

- keep the model id in metadata
- keep the physical table name readable
- do not rely on a numeric suffix in the table name as the primary identity

If a stable numeric model id is still required internally, it should stay in builder/backend metadata, not be the main physical table name.

## Field Naming Rule

There are two possible policies.

### Preferred PostgreSQL policy

Use a short field storage key inside the table.

Pattern:

- `<field_storage_key>`

Examples inside `pb_customer_profile`:

- `first_name`
- `last_name`
- `email`

This is the cleaner PostgreSQL style.

### Legacy-compatible policy

If compatibility with older integration expectations is required, use:

- `<table_storage_key>_<field_storage_key>`

Examples inside `pb_customer_profile`:

- `customer_profile_first_name`
- `customer_profile_last_name`

This is possible, but it should be treated as a deliberate compatibility mode because it creates longer column names and more noise.

## Recommended V2 Position

If there is no hard legacy dependency, prefer:

- readable table prefixing
- short field names inside the table

If there is a hard legacy dependency, allow a configurable physical naming policy at the backend layer.

That means the builder should store:

- visible field label
- logical field key
- optional physical storage key override

The builder UI should not force users to think in raw PostgreSQL column names unless they intentionally open advanced settings.

## System Columns

Each managed table should have generated system columns.

Recommended baseline:

- `_id`
- `_guid`
- `_created_at`
- `_updated_at`
- `_row_version`

### Recommended meanings

- `_id`
  - numeric primary key
  - PostgreSQL: `bigint generated by default as identity`
- `_guid`
  - stable UUID
  - backend default generation
- `_created_at`
  - creation timestamp
- `_updated_at`
  - last update timestamp
- `_row_version`
  - optimistic concurrency version

## PostgreSQL Note About Auto-Updating Rowstamp

PostgreSQL does not provide a SQL Server-style auto-updating rowstamp column in the same way.

If V2 must avoid triggers, the safest early recommendation is:

- keep `_updated_at` and `_row_version`
- update them in the backend write layer on every mutation

This means:

- no trigger dependency
- predictable application behavior
- easier portability

Recommended V2 rule:

- do not depend on database triggers for normal builder-generated tables
- let the backend/service layer own automatic maintenance of `_updated_at` and `_row_version`

## Indexes

Platform Builder V2 should assume that managed tables need automatic index generation.

Baseline indexes:

- primary key on `_id`
- unique index on `_guid`
- indexes for relation columns
- indexes for frequently filtered fields when configured

Optional indexes depending on field behavior:

- unique business-key index
- text-search support index
- composite indexes for common filter patterns

The builder should not expose all of this in the basic UX at first, but the schema model should leave room for it.

## Relationships

The data-schema model should support explicit relationships such as:

- one-to-many
- many-to-one
- optional parent-child collections

When a relation is modeled, the backend should generate:

- relation column naming
- relation indexes
- referential behavior

The builder should treat relation authoring as a schema concern, not as a screen-layout concern.

## External Or Static Tables

V2 should support creating a data schema from an existing static or system-owned table such as:

- `users`
- other platform-owned tables

Recommended model:

- map a builder data schema to an existing physical table
- mark that schema as externally managed or structurally locked
- allow creation and editing of UI schemas on top of it
- disallow physical schema edits from the builder

This is an important V2 capability because not every useful screen starts from a builder-owned table.

## Locked Existing Table Mode

When a schema is backed by an external locked table:

- the builder may create views or UI schemas
- the builder may reorder, hide, group, and configure visible fields
- the builder may not:
  - add physical fields
  - change physical field types
  - rename physical storage keys
  - change backend-owned constraints

This rule should be visible in the authoring UX and enforced by the backend contract.

## Form Builder Implications

The Form Builder should reflect these rules without exposing all storage details by default.

Recommended UX implications:

- normal users work with visible names and logical field labels
- storage keys and physical table names live in advanced schema settings
- locked schemas disable physical model changes
- UI-only authoring remains possible where policy allows it

## Final Recommendation

The V2 model should explicitly separate:

- business naming
- logical schema keys
- physical PostgreSQL storage naming

The early recommended default is:

- table prefix: `pb_`
- readable table names
- short field names unless compatibility mode is required
- generated system columns owned by the backend write layer
- automatic index and relationship support
- support for external locked tables with editable UI schemas on top
