# Future Implementations

This document tracks future implementations that are useful for the stack but are not yet part of the live runtime contract.

If this document conflicts with the current working-set documents under:

- `docs/codex-native-repo.md`
- `docs/maestro/module-orchestrator-v2-spec-pack/`

the working set takes precedence.

## Purpose

This document exists as a compact backlog for future architecture and runtime improvements:

- what we want to add;
- why it matters;
- where the source-of-truth boundary should live;
- which acceptance criteria define completion.

  - acceptance criteria.

## Backlog

### 1. Automate `agents/openai.yaml` consistency for Codex-native skill bundles

#### Status

Proposed.

#### Context

The current Codex-native runtime already stores `agents/openai.yaml` inside each repo-local skill bundle:

- `.agents/skills/maestro/agents/openai.yaml`
- `.agents/skills/charlie/agents/openai.yaml`
- `.agents/skills/grant/agents/openai.yaml`

These files are currently authored directly and may drift from the intent expressed in `SKILL.md` or adjacent skill metadata. The file remains a UI and harness metadata layer, not a behavior contract:

- `display_name`
- `short_description`
- `default_prompt`
- optional icons
- optional dependency declarations
- policy flags such as `allow_implicit_invocation`

This does not currently block skill behavior because the core logic is defined by:

- `SKILL.md`
- the active Codex-native source-of-truth surfaces in `.agents/skills/` and `.codex/`

#### Why This May Matter

- It would reduce manual drift between `SKILL.md` and product-facing skill metadata.
- It would make skill packaging more repeatable as the Codex-native repo grows.
- It would let us describe tool dependencies and policy in a machine-readable format rather than only in prose.

#### Desired Outcome

For each skill bundle, we want a lightweight consistency mechanism for:

- `.agents/skills/<skill>/agents/openai.yaml`

The file itself must be treated as an adapter/output, not as a new source of truth.

#### Source-Of-Truth Boundary

The source of truth should remain in the Codex-native runtime surfaces.

Preferred approach:

- add an explicit metadata block near the active skill bundle or another Codex-native manifest;
- validate or render `agents/openai.yaml` from that metadata block;
- avoid semantic drift between `SKILL.md` and `agents/openai.yaml`.

Possible homes for the source-of-truth metadata:

- add frontmatter or adjacent metadata inside `.agents/skills/<skill>/`
- add a dedicated Codex-native metadata file under `.agents/skills/<skill>/`
- extend another repo-local Codex-native manifest if one proves stable enough

#### Proposed Scope For The First Implementation

The first implementation should stay minimal and avoid overengineering:

- support `interface.display_name`;
- support `interface.short_description`;
- support `interface.default_prompt`;
- support `policy.allow_implicit_invocation`;
- keep the sync or validation step optional rather than mandatory for all local edits.

Optional later:

- `icon_small`
- `icon_large`
- `brand_color`
- `dependencies.tools`

#### Non-Goals For The First Iteration

- Do not make `agents/openai.yaml` required for skill routing to work.
- Do not move core skill semantics from `SKILL.md` into `openai.yaml`.
- Do not add a new global registry just for one adapter file.
- Do not move skill behavior out of the active Codex-native skill and contract files.

#### Example Implementation Task

Title:

`Add Codex-native openai.yaml sync or validation for repo-local skill bundles`

Task:

Add a small Codex-native metadata path and a sync or validation step for `agents/openai.yaml` across `grant`, `maestro`, and `charlie`, without changing their core invocation semantics.

#### Acceptance Criteria

- Skill source-of-truth has a defined place for UI/export metadata fields.
- `agents/openai.yaml` can be checked or refreshed without hand-edit drift.
- `agents/openai.yaml` does not become source-of-truth and can be safely regenerated or validated.
- Existing skill bundles keep correct `display_name`, `short_description`, and `default_prompt`.
- Documentation explains clearly that `openai.yaml` belongs to the product/harness layer, not to core skill logic.

#### Open Questions

- Where should interface metadata live: frontmatter, adjacent skill metadata, or another Codex-native manifest?
- Should `agents/openai.yaml` be regenerated by default for all repo skills or only checked for drift?
- Should `default_prompt` be authored manually or assembled automatically from skill metadata?
