Используй этот skill, когда задача:
- многосоставная;
- затрагивает больше одного слоя системы;
- не до конца определена;
- может затронуть контракты, auth, tenant context, БД, миграции или shared code;
- должна быть сначала спланирована, а уже потом реализована.

Не используй этот skill, если:
- задача тривиальная и локальная;
- меняется только текст/документация;
- пользователь явно попросил маленькую одношаговую правку без плана.

## Обязательный порядок работы

1. Сначала прочитай:
   - корневой `AGENTS.md`;
   - ближайший `AGENTS.md` по текущей директории;
   - связанные `PLANS.md`, `docs/contracts/*`, `docs/adr/*`, если они есть.

2. Собери контекст в формате:
   - **Goal** — что нужно сделать;
   - **Context** — какие файлы, директории, существующие модули, API, страницы, ошибки, документы важны;
   - **Constraints** — архитектурные, безопасностные, tenant, UX, coding-style ограничения;
   - **Done when** — что должно быть истинно в конце.

3. Определи:
   - in scope;
   - out of scope;
   - assumptions;
   - open questions;
   - зависимости;
   - touched areas.

4. В `touched areas` обязательно перечисли:
   - frontend / backend / docs / tests;
   - app/service/package/modules;
   - API changes;
   - DB / migrations;
   - auth / permissions / tenant context;
   - observability / logging / feature flags / rollout, если применимо.

5. Составь план только по текущей задаче.
   Не расширяй scope.
   Не “улучшай систему заодно”.
   Не начинай менять код до завершения планирования.

## Формат результата

Верни план строго в такой структуре:

# Plan

## 1. Goal
Кратко и конкретно.

## 2. Scope
Что входит.

## 3. Non-goals
Что точно не входит.

## 4. Current state
Что уже есть в кодовой базе.

## 5. Touched areas
Список файлов, модулей, сервисов, API, БД, миграций, docs, tests.

## 6. Implementation steps
Нумерованный пошаговый план.

## 7. Validation
Какие тесты, проверки, smoke steps, lint/build/typecheck нужны.

## 8. Risks
Технические и продуктовые риски.

## 9. Rollback
Как откатить изменение, если оно пойдет не так.

## 10. Open questions / assumptions
Только действительно важные вопросы и допущения.

## Правила
- Не начинай редактировать файлы, пока план не готов.
- Если видишь архитектурный риск, явно напиши `Architecture Gate needed`.
- Если задача слишком большая, явно предложи `Feature Split`.
- Если информации не хватает, сначала уточни критичные вопросы, а не придумывай.
- Если можно безопасно продолжать с assumptions, перечисли assumptions явно.
